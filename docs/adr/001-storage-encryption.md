# ADR-001: 履歴の保存と暗号化の方式

**日付:** 2026-10-17
**ステータス:** 決定済み

## 背景
クリップボード履歴にはパスワードなどの機密情報が含まれうる。保存ファイルをテキストエディタで開いても内容が読めないこと、鍵がファイルに平文で置かれないこと、パスフレーズ入力が不要であることが求められる。配布は macOS(Apple Silicon)と Windows(x64)で、GitHub Actions でビルドする。

## 決定
- SQLite(rusqlite 0.40、`bundled` feature)に保存する。
- 1件ずつ AES-256-GCM(aes-gcm 0.11)で暗号化する。列として平文で持つのは `id` と `copied_at`(コピー日時)だけとし、本文・種類・コピー元アプリ名・ピン留め状態はまとめて暗号化した BLOB に入れる(ただし、BLOB の長さや行数など、暗号化では隠せない情報は「影響」に挙げる)。nonce は1件ごとにランダムな 96bit を生成し、AAD に形式バージョンと `id` を入れて行の入れ替えを検出する。
- 鍵(32 バイト)は OS のキーチェーンに保存する(keyring-core + apple-native-keyring-store + windows-native-keyring-store)。
- 起動時に全件を復号してメモリ上に保持し、検索・重複判定・上限処理はメモリ上で行う(1,000件・検索 200ms 以内)。
- 鍵の取り違えを検出するため、既知の文字列を暗号化した値(key check)を `meta` テーブルに保存する。DB が存在するのに鍵が取得できない、または key check が復号できない場合は、履歴を読み込まず、DB へ書き込まず、新しい鍵も作らない。

## 理由
- `bundled` のみなら Windows の CI でも C コンパイラだけでビルドでき、OpenSSL・perl に依存しない。
- メタデータ(種類・コピー元)まで暗号化することで、平文の列を日時だけに抑えられる(暗号文の長さなどは見える)。暗号化した列は SQL で検索できないが、1,000件程度ならメモリ上の検索で要件を満たせる。
- 鍵を OS のキーチェーンに置くことで、パスフレーズ入力なしで鍵をファイルに平文で置かずに済む。

## 却下した代替案
- SQLCipher(`bundled-sqlcipher-vendored-openssl`): DB 全体を暗号化できるが、Windows の CI に OpenSSL のビルド(perl・make)が加わり、ビルドが壊れやすくなる。
- 本文だけ暗号化し、種類・コピー元を平文の列に置く方式: SQL で絞り込めるが、どのアプリから何時に何の種類をコピーしたかが平文で残る。
- パスフレーズから鍵を導出する方式: 起動のたびに入力が要り、要件(入力不要)に反する。

## 影響
- 復号した内容はメモリ上に平文で存在する(プロセスのメモリを読める攻撃者には無力。許容する)。
- ファイルを直接読むと、`id`、`copied_at`、件数、暗号文の長さ(本文の長さの目安)、画像があるかとその大きさが分かる。内容、種類、コピー元は分からない。
- keyring-core は 1.0 以上だが、エコシステムは単独メンテナへの依存がある。aes-gcm・rusqlite は 1.0 未満で、更新時に破壊的変更が入りうる。
- 署名なしアプリでのキーチェーンのアクセス許可ダイアログの出方は未確認(実機で確認する)。
- 画像は本体を別テーブルに暗号化して置き、必要なときだけ復号する(メモリ使用量を抑えるため)。
